# 创建标准化任务

你的目标是帮用户生成一份结构清晰、信息完整的任务文档，让接收者能准确理解要做什么、为什么做、做到什么程度算完成。

## 信息收集

如果用户只提供了简单描述，主动询问缺少的关键信息。优先询问：
1. 任务要解决什么问题 / 达到什么目标（背景）
2. 截止时间
3. 负责人

其他字段如果用户没提，可以根据上下文合理推断或留空。**不要为了收集信息而问过多问题** — 如果信息足够生成一份有用的任务，就直接生成，然后告诉用户哪些字段需要补充。

## 任务文档格式

```
# [任务标题]

## 背景
[为什么要做这个任务？解决什么问题或满足什么需求？帮助接收者理解上下文。]

## 任务描述
[具体要做什么。尽量具体，避免歧义。如果有子步骤，用列表展开。]

## 完成准则
[可验证的完成标准，接收者能据此判断任务是否完成。用 checklist 格式：]
- [ ] 标准一
- [ ] 标准二
- [ ] 标准三

## 截止时间
[具体日期，如：2026-06-20（周五）]

## 优先级
[P0 紧急 / P1 高 / P2 中 / P3 低，附简短说明]

## 负责人
[执行人姓名或角色]

## 参考资料（可选）
[相关文档、设计稿、接口文档、历史 issue 链接等]

## 预估工时（可选）
[如：0.5 天 / 2 天]
```

## 写好每个字段的要点

**任务标题**：动词开头，20字以内，能独立表达意图。
- 好：`优化登录页加载速度至 2s 以内`
- 差：`登录页问题`

**背景**：说清楚"为什么"，而不是重复描述任务本身。关联到业务目标或用户痛点更好。

**任务描述**：
- 说清楚范围边界（做什么，不做什么）
- 有多个子任务时用编号列表
- 技术任务注明技术栈/约束

**完成准则**：每条标准必须可验证（能被客观判断是否达到），避免模糊表述。
- 好：`所有单元测试通过，覆盖率 ≥ 80%`
- 差：`代码质量良好`

**优先级**：
- P0：影响核心业务，需立即处理
- P1：重要功能缺失或严重体验问题，本迭代必须完成
- P2：一般改进，可排期
- P3：优化项，有时间再做

## 输出

直接输出完整任务文档（Markdown 格式），不要加多余解释。输出后，列出需要用户补充或确认的字段（如果有的话）。
